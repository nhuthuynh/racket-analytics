# CI-REDUNTIL-HANG decisions

Small decisions for ticket CI-REDUNTIL-HANG: the integration job's step "Rows waiting on a story (red_until)" hung on `main` in run 37961668800. One file per ticket (PO rule 2026-10-07). The shared decision log is consolidated by the sprint's DOCS/RETRO ticket.

## Root cause (evidence)

Run 37961668800, job 113925768741, push of the PR #49 merge, head `5cc1742`. The backend suites passed (`2793 passed, 1 skipped in 226.47s`). The red_until step started at 16:52:51. The job limit cancelled it at 17:07:58. The runner then killed the orphan `uv` and `pytest` processes. The job log has no line of pytest output until 16:54:53. At 16:54:53 comes the first `+++ Timeout +++`, after 122 s, so the step's first row (`tests/features/test_account_deletion.py::test_delete_account`) used up the whole 120 s per-test timeout. Next come 27 `F` and a second `Timeout` at 17:00:16 (row 28, `test_it_03_08_both_sessions_end_and_the_purge_leaves_nothing`). After that the log is silent until the cancel. Both dumps show the same thread: the API's AnyIO worker in `video_ingest/service.py:418 write_chunk` → `platform/storage.py:173 upload_part` → botocore → `http/client.py _read_status` → `socket.recv_into`. That thread is waiting on the object store to answer an S3 `UploadPart`. The `integration-reports` artifact 11631879018 has no `red-until.xml`, because the step was cancelled before pytest wrote it. Its download URL returned HTTP 403 through the agent proxy, so the test ids above come from the job log.

1. **The rows depend on the object store's write throughput.** A scratch plugin counted the bytes each row sends to the store (`put_bytes` + `upload_part`): 61 of the 88 rows upload the 1.72 MB clip at least once, and the selection sends **174,331,413 bytes** in all. `test_delete_account` and `test_signing_in_again_starts_empty` send 7,758,933 each, and `test_it_03_08_both_sessions_end_…` sends 10,345,244. The command was `PYTHONPATH=<scratch> uv run --no-sync pytest -q -p no:cacheprovider -p s3bytes -m "red_until and not nightly"`, with result `88 failed … in 29.43s`.
2. **On the CI runner the store took writes at about 64 KiB/s.** CI-IT0213-HANG measured this rate (13.33 s per 0.86 MB, 26.67 s per 1.72 MB) and saw the same stack. At that rate, 7,758,933 bytes take 118 s and 10,345,244 bytes take 158 s. This matches the log: row 1 timed out at 120 s, row 2 finished just under the limit, and row 28 timed out. The remaining ~144 MB would need about 37 min.
3. **Nothing bounded the step, and the report hid it.** The per-test timeout (120 s) stops one row, not the run. The step had no `timeout-minutes`, so the job's 20 min was the only limit. `red_until_report.py` counted a row that pytest-timeout stopped as an expected red, so even a finished run would have looked green.
4. **Not the cause:** a lock or connection left over from the backend suites. That run ended at 16:52:51 with every test passed, and the red_until step runs in its own process. It is also not code reached from merged stories (delete/purge): the same head passed on PR run 37957230516, and locally the step behaves the same on a fresh stack and after a full backend run.

Local reproduction, `backend/`:

- On a fresh stack (Postgres 16 via `scripts/dev-postgres.sh`, SeaweedFS 3.97 via `scripts/dev-objectstore.sh`), the CI step command 30 times gave `88 failed` every time in 21.4–25.6 s. The longest run took 31 s, and there were 0 timeouts.
- On a Compose stack with the CI flags (`docker compose -p qaru … up -d --wait postgres objectstore mailpit tracing`), the CI sequence was the backend suites (`-n auto`, CI selection) giving `2793 passed, 1 skipped in 200.11s`, then the step giving `88 failed … in 29.50s`, with 0 timeouts. The store did not slow down locally, which matches CI-IT0213-HANG.
- With every S3 call going through `tests/support/slow_store.py` at `CI_WRITE_RATE`, the old step had finished only 4 rows after 330 s (`timeout 330 … -p viaslow`, rc 124). This is the CI pattern.

Why the store slows down on the runner is still not known (CI-IT0213-HANG follow-up). This ticket does not fix the store. It makes the step independent of it: the step now stops in time and names the cause.

## Follow-ups (not in this ticket)

- **Why the store slows down** (owner: sre-devops-engineer). The next slow run's `reports/objectstore.log` should show what the store is doing. When it happens, the step now fails within about 2 minutes and names the rows.
- **Fewer bytes in the red_until rows** (owner: senior-qa-engineer, a TCR per file). The account-deletion rows (`test_account_deletion.py`, IT-03-08, IT-03-13, and the IT-03-12 `delete_account` rows) never probe the video. They could use `rate_burst.receive_minimal_video`, which would cut about 60 MB. The Full Tag and label rows need a probed clip. Not done here: it changes accepted tests, and the step is already bounded.
- **The API thread keeps the upload row lock after a test timeout.** This is the PR #17 backlog item (bounded botocore timeouts and a cap on concurrent chunk writes), owned by senior-backend-engineer with principal-engineer.
