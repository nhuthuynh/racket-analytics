| 2026-11-05 | senior-backend-engineer | **"Confirmed corrections" = every committed row of `match_corrections` whose match is live (`matches.deleted_at IS NULL`), every column.** No filter on kind or undo. Revised in review round 1 (PR #209 F1): the first version also counted tombstoned matches | `backend/src/racket/matches/scorebook/integrity.py` (`sa.select(match_corrections).where(match_id IN live matches)`); unit `test_any_changed_column_changes_the_digest` (12 columns); IT-05-04 `test_it_05_04_a_tombstoned_matchs_corrections_are_not_counted`, `…restore_then_purge_of_a_backup_with_a_tombstoned_match_stays_equal`; scenario "A backup that holds a deleted match stays equal after restore and purge" (red at `1e4a9018`) | The trail is append-only by trigger (migrations 0010, 0011; ADR 0058 context 3), so a committed row is confirmed. All columns, read from the table, so a column added later is covered without editing this module. ADR 0058 rule 4 runs the purge (step 9) before `racket-integrity` (step 10) and the purge cascades a tombstoned match's trail, so counting those rows made every correct restore of a backup with a deleted match report `equal: false` (reviewer's probe: `(6, ff7af38f…)` vs `(3, 9632acc0…)`). | 2026-11-05 | senior-backend-engineer | **Canonical form: one JSON line per row (sorted keys, no spaces, ids as text, timestamps converted to UTC ISO 8601), SHA-256 over the lines in the order `(match_id, version, id)`, each line ending in `\n`.** Empty table → `(0, e3b0c442…b855)` (SHA-256 of no bytes). JSONB key order is not stable across dump and restore, but sorted keys are |
