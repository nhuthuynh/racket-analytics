# 0011. tus server: a tus 1.0.0 core inside the FastAPI app, not a tusd sidecar

- **Status:** Accepted for Sprint 0 (ST-008 design review, held early on 2026-10-03 so the backend lane can start on it). Revisit only through a superseding ADR.
- **Date:** 2026-10-03
- **Deciders:** principal-engineer (R/A)
- **Consulted:** security-privacy-engineer (threat model v0, `docs/security/threat-model-v0.md` §4.1), senior-qa-engineer (through the red-first tests and ADR 0012), senior-backend-engineer (implementer of ST-008)
- **Related:** ST-006, ST-007, ST-008, ST-010; FR-022, FR-024, FR-080; NFR-026, NFR-042, NFR-051, NFR-053, NFR-060, NFR-081; ADR 0008 (stack; this ADR settles its open "resumable upload server" row), ADR 0012 (seam contract), API contract `docs/architecture/api-sprint-00.md`

## Context and problem statement

ADR 0008 left the tus server open: "tusd sidecar (MIT) or a tus 1.0.0 core implemented in FastAPI. Both must pass the upload-resume regression suite." ST-008 needs the answer before code starts. The required behaviours are the tus core: `POST` creation with `Upload-Length`, `HEAD` returns `Upload-Offset`, `PATCH` from that offset, and 409 on an offset mismatch with the upload unchanged [AQS/STACK-06]. Every upload ID must pass the same ownership check as every other resource [AQS/SEC-09, AQS/SEC-03 8.2.2]. Object keys are generated by the server [AQS/SEC-02 5.3.2]. The probe job may only exist once the final byte is stored [AQS/SEC-07 2.3.1] (NFR-060).

## Decision drivers

- **D1. BOLA on every request:** `HEAD` and `PATCH` on an upload must return the same 404 to a non-owner as for a missing upload. The check runs server-side with the same ownership dependency as `/matches/{id}` [AQS/SEC-09; AQS/SEC-03 8.2.2, 8.3.1; AQS/STACK-01 G7.5].
- **D2. Business-flow order:** the probe job must be enqueued if and only if the final byte is durably stored, all or nothing [AQS/SEC-07 2.3.1, 2.3.3] (NFR-060, NFR-047).
- **D3. Stateless, horizontally scalable processes:** no sticky sessions and no per-process locks that correctness depends on [AQS/OPS-04] (NFR-081).
- **D4. Dev/prod parity, fewest backing services:** Postgres, the S3-compatible store and nothing else [AQS/OPS-05] (NFR-080); ADR 0008 [AQS/ENG-04 push back on speculative over-engineering].
- **D5. The red-first tests already exist** (ADR 0012). They drive tus over httpx `ASGITransport` against the FastAPI app [AQS/STACK-01], and the BOLA endpoint inventory reads the FastAPI routes. 74 red tests name these seams (ADR 0012 evidence).
- **D6. Production S3 multipart rules:** every part except the last must be at least 5 MiB. tusd's own documentation describes this limit (evidence below). Phone clients send chunks of arbitrary size.

## Considered options

1. **tusd sidecar** (MIT, ADR 0008) with the S3 store, behind the API's auth. HTTP hooks call the API.
2. **A tus 1.0.0 core inside the FastAPI app**: creation, HEAD and PATCH routes. Postgres holds the upload state and a row lock, and the bytes go into an S3 multipart upload.
3. **No tus: S3 presigned multipart URLs issued to the browser** (the "S3 multipart equivalent" that AQS Implications mentions).
4. **Do nothing:** a single-request `PUT` upload.

## Decision outcome

**Chosen option: 2, a tus 1.0.0 core inside the FastAPI app.** It is the only option that satisfies D1, D2, D3 and D5 without another backing service or a protocol-level workaround.

- **D1.** tusd's hook list has no blocking hook on `HEAD` or `PATCH`. The blocking hooks are `pre-create`, `pre-finish` and `pre-terminate` (evidence E1). Per-request ownership checks on an existing upload would need a separate authenticating reverse proxy in front of tusd, which is a second authorisation implementation to keep in step with the BOLA matrix.
- **D2.** `post-finish` is non-blocking, and hook order is "not guaranteed" (E1). Enqueueing the probe from it is therefore at-least-once and outside our transaction. The FastAPI core commits "upload complete + probe job queued" in one Postgres transaction (ADR 0008 part B: transactional enqueue).
- **D3.** With S3 storage, tusd's default lock is an in-memory lock. Its docs say "tusd does not yet offer distributed locks" and recommend sticky sessions when scaling out (E2, E3). Option 2 serialises requests with a Postgres row lock, so any API replica can serve any request.
- **D5.** Option 2 keeps the existing tests and routes unchanged. Option 1 would move upload routes out of the app the BOLA inventory reads, and its tests would need a running tusd binary.

### Design (binding for ST-008; HTTP details are in `docs/architecture/api-sprint-00.md` §6)

**Routes**, on the FastAPI app and in the BOLA matrix:
- `OPTIONS /uploads`: discovery. `Tus-Version: 1.0.0`, `Tus-Extension: creation`, `Tus-Max-Size`.
- `POST /matches/{match_id}/uploads`: creation. The caller must own the match, and the match must have no upload session yet.
- `HEAD /uploads/{upload_id}`
- `PATCH /uploads/{upload_id}`

**Upload state** lives in the `video_ingest` context, in Postgres. The `UploadSession` aggregate holds:
- `id` (UUIDv4), `owner_id`, `match_id`;
- `length`, `offset`;
- `object_key` (generated by `ObjectKeyPolicy`, never from user input), `s3_upload_id`;
- `parts[]` (part number, ETag, size), `staged[]` (offset, size, key);
- `status`: `receiving`, `complete` or `expired`.

The pure-domain rules come from sprint-00 §5: an offset mismatch raises `OffsetMismatch` and leaves the state unchanged; a chunk past `length` is rejected; a chunk at the right offset advances it; `is_complete` holds only when offset equals length.

**PATCH algorithm** (judgment; each step is fail-closed [AQS/SEC-12]):
1. Validate the request before reading the body:
   - session → 401;
   - `Tus-Resumable` → 412;
   - owned upload (`WHERE id = :id AND owner_id = :me`) → 404;
   - `Content-Type: application/offset+octet-stream` → 415;
   - `Upload-Offset` is an integer → 400;
   - `Content-Length` present → 411, and no larger than `UPLOAD_MAX_CHUNK_BYTES` → 413;
   - `Upload-Offset` equals the stored offset → 409;
   - `offset + Content-Length` no larger than `length` → 413.

   The 409 check runs before the length check, so a wrong offset is always a conflict (the regression suite pins this).
2. Read the body. This is bounded by step 1. It may be spooled to a size-capped temporary file for one request only, which is allowed as a "brief single-transaction cache" [AQS/OPS-04]. A body shorter than `Content-Length` (a dropped connection) stores nothing.
3. Take the lock with `SELECT … FOR UPDATE NOWAIT` on the session row. If the row is already locked, return 409 and the client re-HEADs. Re-check that the offset is unchanged.
4. Write the bytes, either as a multipart part or as a staging object:
   - **As a part:** if `staged bytes + chunk ≥ UPLOAD_PART_MIN_BYTES` (5 MiB), or this is the final chunk, upload `staged chunks + chunk` as part `n+1`, where `n` is the number of committed parts. Then record the part and clear `staged[]`.
   - **As a staging object:** otherwise, store the chunk as the staging object `staging/{upload_id}/{offset:020d}` and record it.

   Each byte is written to staging at most once and read back at most once, so a client sending tiny chunks costs at most about 2x I/O, never a quadratic tail rewrite (judgment).
5. If the new offset equals `length`, complete the upload:
   - call `CompleteMultipartUpload` with the committed parts;
   - mark the session `complete`;
   - call `Match.mark_uploaded(media_asset_id)`;
   - insert the `probe` job row (`JobKey(match_id, pipeline_version, "probe")`) with the W3C trace context injected [AQS/OPS-06].
6. Commit, then delete the staging objects. This is best-effort; leftovers are swept with the expired uploads (FR-024, Sprint 1).

**Crash and retry analysis** (judgment):
- A failure before commit leaves the offset unchanged, so a retried PATCH re-uploads the same part number. S3 replaces a part that is uploaded again, and only the committed ETag is used.
- A crash after `CompleteMultipartUpload` but before commit: the retry finds the multipart upload gone. It then completes idempotently by checking that the final object exists with size `length`, and commits.
- Staging objects are keyed by offset, so a retry overwrites rather than duplicates.

**Deliberate deviation from a tus SHOULD:** a PATCH is atomic. On a dropped connection we keep nothing from that request, rather than "as much of the received data as possible". The cost is re-sending at most one chunk. The client chunk size is 8 MiB (ST-010; judgment). This keeps the offset equal to durably stored bytes with no partial-part bookkeeping.

**Deliberate exception to "one aggregate per transaction" (ddd-guidelines §4.1):** step 5 changes `UploadSession` and `Match` and inserts a job row in one transaction. Driver D2 requires that the probe exists if and only if the final byte is stored. Splitting the steps would need an outbox relay that we do not have yet, which would be speculative for Sprint 0 [AQS/ENG-04]. This is recorded as hotspot H3 in `docs/architecture/eventstorming.md`. If a second consumer of `MatchUploaded` appears, we introduce an outbox.

**Not in Sprint 0** (Sprint 1, ST-013+): the checksum and expiration extensions [AQS/STACK-06], magic-byte and duration validation (FR-023, NFR-053), `DELETE` (termination), per-user quotas and rate limits [AQS/SEC-02 5.2.4; AQS/SEC-07 2.4.1].

## Pros and cons of the options

### Option 1: tusd sidecar
- Good: a mature implementation of the tus protocol, including extensions, and MIT-licensed (ADR 0008).
- Bad: no per-request authorisation hook on HEAD/PATCH (E1), so BOLA needs an extra authenticating proxy (D1).
- Bad: probe enqueueing via the non-blocking, unordered `post-finish` hook (E1) breaks D2's "in one transaction".
- Bad: with S3 there is only a single-process lock unless sticky sessions are used (E2, E3), which breaks D3.
- Bad: it keeps a `.info` object per upload in the bucket next to the media (E4), adds a fourth runtime service, and needs strong read-after-write consistency from the store (E5).
- Bad: the red-first tests and the BOLA inventory (ADR 0012) would need rework.

### Option 2: FastAPI tus core
- Good: one auth path and one BOLA dependency; a transactional enqueue; stateless replicas; no new service; the existing tests apply as they are.
- Bad: we own protocol code. The core is small (three routes and one aggregate), and the mandatory upload-resume regression suite pins it (testing-strategy §5).
- Bad: we must implement the extensions ourselves in Sprint 1 (checksum, expiration).

### Option 3: presigned S3 multipart URLs
- Good: bytes bypass the API entirely, so the API process does the least work.
- Bad: it is not tus, so it fails the accepted tus 1.0.0 requirement (NFR-026, FR-022 and [AQS/STACK-06]).
- Bad: it puts bearer-like signed URLs in the browser for writes [AQS/SEC-05 14.2.1], and the client must track part ETags.
- Bad: the "final byte stored → enqueue" step would rely on a client call, which breaks D2.

### Option 4: single PUT
- Bad: no resume. It fails FR-022 and NFR-042 outright.

## Consequences

- **Good:** ST-008 can start now against `docs/architecture/api-sprint-00.md`. The QA seam paths `UPLOAD_CREATE` and `UPLOAD_RESOURCE` in `backend/tests/support/contract.py` stay valid, so no test change is needed.
- **Trade-offs accepted:**
  - Upload bytes flow through the API process, so request size and time limits must be set at the ingress (SRE, ST-001/ST-002).
  - The API needs S3 write credentials for the media bucket (least privilege: no `DeleteBucket`, no other buckets) [AQS/SEC-06 13.3.2].
- **Follow-up work:**
  - BE: implement ST-008 as above.
  - SRE: add `UPLOAD_MAX_BYTES`, `UPLOAD_MAX_CHUNK_BYTES`, `UPLOAD_PART_MIN_BYTES` and `API_PUBLIC_PATH_PREFIX` to `infra/env.example` (api-sprint-00 §9).
  - FE: tus-js-client with `chunkSize` 8 MiB and the endpoint under the `/api` prefix.
  - Sprint 1: checksum and expiration extensions, and the expiry sweeper deleting staging objects and aborting multipart uploads (FR-024, NFR-066(d)).
- **Re-evaluation trigger:** if upload traffic makes API replicas I/O-bound (NFR-042 or latency SLIs breached), raise a superseding ADR for direct-to-store uploads with a server-side completion check.
