## 10. DC-4 decision: coarsen `retry_at` on keys that are not the caller's own

- **Decision (security-privacy-engineer, 2026-11-13):** **coarsen.** The timing disclosure of `A-LIMIT` (data-classification §4 DC-4) is not accepted as a residual.
- **Rule:** on a 429 from a limiter key that is **not** the signed-in caller's own account key (`link:email:<email_key>`, `link:ip:<ip>`, `match:create:ip:<ip>`), `error.retry_at` is the refused request's time plus the full window, and `Retry-After` is the window in seconds. Neither depends on the oldest stored `at`. Account keys (`match:create:<account id>`, `upload:create:<account id>`) and `next_slot_at` on `GET /me/quota` keep the exact value, because they disclose only the caller's own activity.
- **Why:** today `retry_at = oldest at + window` (`RateLimiter.hit`) tells an anonymous caller, to the second, when the oldest counted sign-in request for an address or IP was made, which is a timing side channel on someone else's sign-in activity (ASVS 5.0 V6 anti-enumeration; exact requirement id is judgment). The cost is that an honest caller may wait up to one window (600 s by default, `AUTH_WINDOW_SECONDS`) longer than needed; sign-in limits are rarely hit by honest users (judgment).
- **Alternatives considered:** (a) accept the disclosure as a residual: needs the PO in an ADR (P19) for a fix that is a few lines; rejected. (b) round up to the next window boundary: still leaks the oldest request's window slot; rejected. (c) drop `retry_at` from the body and send only `Retry-After`: breaks the api-sprint-01 §1.1 error contract; rejected.
- **Implementation:** an XS fix ticket, tier 2 (`platform/ratelimit.py` is tier 2), owner senior-backend-engineer, proposed id **SEC-DC4** (the engineering-manager adds it to sprint-06 §3 or the Sprint 7 backlog; P2 like SEC-R05). Red test first: a 429 on `link:email` six minutes after the first counted request returns `retry_at` = now + 600 s, not first + 600 s. Gate: before G-DEPLOY (ADR 0059). Until it merges, data-classification §4 shows DC-4 as "Decided, fix pending".

## 11. DC-1 decision: at-rest encryption criterion for ADR 0034, gate G-DEPLOY

- **Decision (security-privacy-engineer, 2026-11-13):** ADR 0034 gets an at-rest storage criterion, and it binds at **G-DEPLOY** (before any deployment reachable by anyone but the developer, ADR 0059 gates), not only before beta: a staging copy with real data is exposed the same way as a beta.

  - **E9 At rest** (NFR-063, `E-PG`, `E-S3`, `E-HIGH`): the Postgres data volume (or managed instance storage), the media bucket and the backup target are encrypted at rest by the host or provider with AES-256 (or the provider's equivalent); the bucket has default encryption on and refuses unencrypted puts; keys are held by the provider's key service or a host key store, never on the encrypted volume; the dev and E2E Compose stacks are exempt because they hold only demo data on localhost (ADR 0051).
